# Dashway 채팅 백엔드 정책

이 문서는 Dashway 채팅 백엔드 V1에서 합의한 기획 및 정책을 정리한다.

## 프로젝트 범위

- 채팅 백엔드는 `apps/chat/back`에 독립 서비스로 둔다.
- 채팅 프론트엔드는 `apps/chat/front`에 둘 수 있지만, 이번 정책의 구현 범위에는 포함하지 않는다.
- 루트 실행 스크립트, 루트 워크스페이스 연결, 루트 Gradle 멀티프로젝트 구성은 이번 범위에서 제외한다.
- V1에서는 테스트 코드를 작성하지 않는다.

## 기술 방향

- Kotlin, Spring Boot, Gradle, PostgreSQL을 사용한다.
- API 조회와 일부 상태 변경은 GraphQL로 제공한다.
- 실시간 채팅 동작은 WebSocket/STOMP로 처리한다.
- 채팅 백엔드는 8081 포트에서 실행한다.
- 채팅 V1에서는 Redis를 사용하지 않는다.
- 실시간 전달은 단일 서버 전제에 맞춰 Spring STOMP 내장 브로커를 사용한다.

## 데이터 저장 정책

- 기존 PostgreSQL 데이터베이스를 사용한다.
- 채팅 데이터는 별도 `chat` 스키마에 저장한다.
- 채팅 서비스에는 사용자 프로필 정보를 복사하지 않는다.
- 채팅 데이터에는 사용자 식별자만 저장한다.
- 사용자 이름, 이미지, 이메일 같은 프로필 표시는 다른 서비스나 프론트엔드에서 처리한다.
- 채팅방 삭제와 메시지 삭제는 실제 삭제가 아니라 삭제 상태를 기록하는 방식으로 처리한다.

## 인증 정책

- 채팅 백엔드는 토큰을 직접 검증하지 않는다.
- 채팅 백엔드는 `context-api`에 토큰 유효성 확인을 요청한다.
- GraphQL 요청은 요청 시작 시 한 번 토큰을 확인한다.
- WebSocket 연결은 최초 연결 시 한 번 토큰을 확인한다.
- WebSocket 명령마다 토큰을 다시 확인하지 않는다.
- `context-api`가 토큰을 유효하지 않다고 응답하거나, 검증 요청에 실패하면 인증 실패로 처리한다.
- 토큰 검증 응답에서 채팅 백엔드가 사용하는 핵심 값은 사용자 식별자이다.
- 토큰 검증 API는 V1에서 별도 서비스 간 secret 없이 사용한다.

## GraphQL 책임

GraphQL은 다음 기능만 담당한다.

- 채팅방 목록 조회
- 메시지 목록 조회
- 채팅방 생성
- 채팅방 삭제
- 채팅방 즐겨찾기 변경

GraphQL은 다음 기능을 담당하지 않는다.

- 메시지 전송
- 메시지 수정
- 메시지 삭제
- 채팅방 멤버 초대
- 채팅방 멤버 강퇴
- 공개 채널 참가
- 읽음 처리
- typing 표시
- 첨부파일

위 기능들은 WebSocket/STOMP 또는 후속 API에서 별도로 다룬다.

## 채팅방 정책

- 채팅방 유형은 1:1 채팅과 그룹 채팅으로 나눈다.
- 채팅방 생성 시 참가자 목록에는 생성자 본인이 포함되어야 한다.
- 참가자 목록에 중복 사용자가 있으면 생성할 수 없다.
- 1:1 채팅은 정확히 두 명만 참여할 수 있다.
- 같은 두 사용자 사이에는 활성 1:1 채팅방을 하나만 유지한다.
- 1:1 채팅방은 공개 채널이 될 수 없다.
- 1:1 채팅방에는 별도 제목을 저장하지 않는다.
- 그룹 채팅방은 생성자를 포함해 2명 이상 100명 이하가 참여할 수 있다.
- 그룹 채팅방은 공개 또는 비공개로 만들 수 있다.
- 그룹 채팅방 제목은 선택 사항이다.
- 채팅방 생성자는 방 소유자가 된다.
- 나머지 참가자는 일반 멤버가 된다.
- 채팅방 삭제는 방 소유자만 할 수 있다.
- 삭제된 채팅방은 목록과 메시지 조회에서 보이지 않는다.

## 공개 채널 정책

- 공개/비공개 정책은 그룹 채팅방에만 적용한다.
- 공개 그룹 채팅방은 채팅방 목록에서 발견할 수 있다.
- 공개 그룹 채팅방이라도 참가자가 아니면 메시지 목록을 볼 수 없다.
- V1에서는 공개 채널 참가 기능을 제공하지 않는다.
- 참가하지 않은 공개 그룹 채팅방은 목록에서 발견용 정보만 보여준다.
- 참가하지 않은 공개 그룹 채팅방은 즐겨찾기할 수 없다.
- 참가하지 않은 공개 그룹 채팅방은 삭제할 수 없다.
- 참가하지 않은 공개 그룹 채팅방은 멤버 목록을 노출하지 않는다.

## 즐겨찾기 정책

- 즐겨찾기는 사용자별 상태이다.
- 같은 채팅방이라도 사용자마다 즐겨찾기 여부가 다를 수 있다.
- 채팅방 멤버만 해당 채팅방을 즐겨찾기할 수 있다.
- 채팅방 목록은 즐겨찾기된 방만 볼 수 있는 필터를 지원한다.

## 메시지 정책

- 메시지 생성은 WebSocket/STOMP로만 처리한다.
- 메시지 생성 시 클라이언트가 만든 메시지 식별자를 함께 보낸다.
- 클라이언트 메시지 식별자는 재연결이나 재시도 상황에서 같은 메시지가 중복 저장되는 것을 막기 위해 사용한다.
- 클라이언트 메시지 식별자는 낙관적 UI에서 임시 메시지와 서버 확정 메시지를 매칭하는 데 사용한다.
- 메시지 본문 최대 길이는 4000자이다.
- 메시지 수정은 작성자만 할 수 있다.
- 메시지 삭제는 작성자만 할 수 있다.
- 삭제된 메시지는 메시지 목록에서 제거하지 않는다.
- 삭제된 메시지는 삭제 상태로 표시하고 본문은 노출하지 않는다.

## 메시지 목록 정책

- 메시지 목록은 채팅방 멤버만 조회할 수 있다.
- 공개 그룹 채팅방이라도 참가자가 아니면 메시지 목록을 조회할 수 없다.
- 메시지 목록은 최신 메시지부터 보여준다.
- 다음 페이지 조회를 위해 커서 기반 페이지네이션을 사용한다.
- 커서는 메시지 생성 시각과 메시지 식별자를 함께 사용한다.
- 메시지 식별자만으로는 안정적인 시간순 페이지네이션을 보장하지 않는다.

## WebSocket/STOMP 정책

- WebSocket은 실시간 채팅 명령과 방 이벤트 전달을 담당한다.
- WebSocket 연결 시 토큰을 전달하고, 연결 시점에만 인증한다.
- 메시지 생성 명령에는 클라이언트 메시지 식별자가 반드시 포함되어야 한다.
- WebSocket 명령에는 클라이언트가 만든 요청 식별자를 포함하는 것을 원칙으로 한다.
- 명령 성공과 실패는 요청 식별자를 기준으로 클라이언트가 매칭할 수 있어야 한다.
- 채팅방 변경 사항은 하나의 방 이벤트 형식으로 전달한다.

## 검증 정책

- V1에서는 테스트 코드를 작성하지 않는다.
- 빌드와 수동 확인으로 검증한다.
- 수동 확인 대상은 다음과 같다.
  - 토큰 검증 성공과 실패
  - 인증된 사용자의 채팅방 생성, 목록 조회, 삭제
  - 인증되지 않은 요청 실패
  - 공개 그룹 채팅방 발견
  - 비참가자의 공개 그룹 메시지 조회 실패
  - 채팅방 멤버만 즐겨찾기 가능
  - 정상 WebSocket 연결 성공
  - 비정상 WebSocket 연결 실패
